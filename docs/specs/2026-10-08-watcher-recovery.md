# 重启恢复后的 Claude 会话监听

日期：2026-10-08

## 问题与修复

此前 JSONL 中断监听仅在接收到工作态 Hook 时建立。应用快照或离线桥接快照可以恢复「工作中」卡片，但加载会话历史不会建立监听；没有新 Hook 的长工具回合因此缺少实时中断监听。通过会话记录补认完成时，也没有统一清理监听。

本轮将监听资源与 SessionStore 的最终状态同步：

- 每个会话事件处理后，读取最新会话状态；Claude 的工作、压缩和待审批状态保持监听，已完成、空闲、结束或移除状态停止监听。
- 重启恢复仍通过现有历史加载事件进入同一个流程；已完成的历史可以先纠正旧的工作快照，不会建立多余监听。
- 跨 MainActor 操作资源后重新核对最新状态，避免等待执行的旧资源操作覆盖刚到达的 Stop 或新回合。
- Codex 和 CodeBuddy 不建立 Claude JSONL 监听。
- 为恢复测试注入独立的快照目录、Claude 会话目录和监听接口，不修改用户的真实会话快照或 Hook 配置。

本轮没有重建已断开的审批 socket；待审批请求的重启策略保持现有约束。

## 自动化证据

四个隔离场景通过：

1. 本地应用工作快照恢复后，无新 Hook 也会建立监听；Stop 后停止监听。
2. 应用离线期间生成的桥接工作快照恢复后，无新 Hook 也会建立监听；会话移除后停止监听。
3. 工作快照对应的历史已完成时，卡片纠正为等待输入，并且从未建立监听。
4. 丢失 Stop 时会话记录可以停止监听；新回合建立监听后，旧中断事件不会将其停止。

## 真实安装态验收

本机 Release 已 ad-hoc 签名安装，主二进制与签名后的构建产物 SHA-256 均为
`621174f77d6f1bc12bc7cec014d446127178aa19dd29ce9f89a5b0ed2ab5adc4`。
旧安装版保留在临时备份目录。该产物不是公证发行版。

使用 Claude Code 2.1.195，在独立的临时目录启动 `--print` 回合，仅允许 Bash 运行有限时的等待脚本。脚本进入运行后创建就绪标记，最多等待 120 秒；测试人员写入释放标记后成功退出。

1. 工具进程存在时，原生诊断页显示 Claude「工作中」，JSONL「监听 1」；应用持久化快照同样记录 `processing` 和有效 PID。
2. 通过应用菜单退出 Agent Notch，随后确认原 App 进程消失、本地 socket 消失，而 Claude Bash 工具进程仍存在。
3. 重新启动安装版，刘海立即出现同一 Claude Bash 任务「工作中」；诊断页再次显示「监听 1」，恢复记录包含会话记录和桥接快照。
4. 工具尚未释放时再次核对进程：工具持续存在，App 已是新进程；同一 Claude 快照的 `lastActivity` / `lastHookEventAt` 仍为退出前的时间。这表明恢复监听没有依赖该 Claude 回合的新 Hook。
5. 释放工具后，真实 JSONL 工具结果为 `is_error: false` 和 `RESTART_ACCEPTANCE_RELEASED`；CLI 返回 `OK`、成功退出。诊断页显示 Hook 完成裁决「工作中 → 等待输入」，JSONL 监听降至 0，并显示该会话「已停止」。

这证明常规单会话的工具运行中重启、工作态恢复、监听恢复和完成清理链路通过。此次同时存在应用快照与离线桥接快照，不据此单独归因于纯原生发现或其中一种恢复来源；两种恢复入口的独立覆盖由上面的隔离测试提供。

本轮没有实际中断该 Claude 工具，也没有执行权限回写、并行会话或 CodeBuddy 的对应场景；旧中断不影响新回合仅有隔离测试证据。
