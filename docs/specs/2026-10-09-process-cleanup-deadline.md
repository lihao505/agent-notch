# 进程调用总预算覆盖输出收尾

## 本轮证据与范围

接续 `d509405` 的 stdin 收尾修复，检查 stdout/stderr 的主进程退出边界。
先运行有限时真实 OS 子进程夹具：主进程输出后立即退出，子进程保留输出管道，
5 秒后自行退出。现有正常收尾在约 2 秒内返回且释放 stdout 回调，测试通过。
因此本轮没有把“输出读取无限阻塞”当成已复现的问题，也没有重写输出读取器。

随后用同一夹具测试 0.3 秒总预算：旧代码在约 2.15 秒后返回 success，
而非 timedOut，新增回归失败。这是本轮实际确认并修复的缺口。

## 原因与实现

异步与同步 runner 的超时回调都要求 `process.isRunning`。
主进程结束后，即使调用仍在等待继承输出管道的子进程，超时也不再生效。
同时 `finishReading` 一次等待完整的 2 秒，无法及时响应此阶段的取消。

- 超时针对本次 capture 的完整调用，包括 stdin 和输出收尾，而非只针对主进程。
- 已完成 capture 会忽略迟到超时；已有终止逻辑仍检查主进程存活，
  不会仅因后台子进程保留管道而向已结束的主进程 PID 发信号。
- 输出正常收尾保留原有约 2 秒排空窗口；等待期间每 50 ms 检查取消、超时。
- 取消、超时或排空窗口结束时沿用原有关闭读取端、最多 0.25 秒收尾等待。
- 不改变输出上限、UTF-8 尾部解码、结果优先级、进程树身份或 UI 状态实现。
  没有引入第三方依赖，也没有修改用户 Hook 或审批设置。

## 回归与验证

新增 4 项测试：

1. 正常退出但子进程保留输出：及时返回已有输出，弱引用确认生产 stdout 回调释放。
   这项在修复前也通过，是保留现有能力的回归，不是新增修复效果。
2. 异步调用的输出收尾遵守 0.3 秒预算：修复后整条用例约 0.344 秒，返回 timedOut。
3. 同步调用的相同边界：整条用例约 0.324 秒，返回 timedOut。
4. 子进程确认父进程已退出后，主动取消仍能及时返回 cancelled；
   整条用例约 0.221 秒，取消后返回时间断言小于 1.5 秒。

所有夹具自行退出，不访问用户文件，不使用真实 Agent 会话或生产 socket。
ProcessExecutor 针对性 13 项测试通过，完整 xcresult 为 265 passed、0 failed、0 skipped；
88 项 Bridge、30 项 verifier 和发布闸门通过。
Release 无签名构建通过；上一轮 stdin 修复 `d509405` 的 GitHub CI 也已确认通过。
这些证据不替代本轮推送后的 CI、签名、安装或真实交互验收。

## 运行态限制与后续验收

尚未收到手动解锁确认，本轮未安装或覆盖运行中的 Agent Notch。
本轮与之前的审批卡绑定、stdin 修复都不能据此宣称已在安装版生效。

OS 子进程测试不证明真实 Agent 的取消回写、会话状态、监听器清理或刘海动画。
没有声称杀掉了所有后台后代进程，也没有将自然退出后的后台工作强行结束。
生命周期矩阵仍保留同会话双审批、审批中重启、并行混合超时及其他未执行项。
解锁后需安装签名构建，继续真实 CLI 和原生界面验收。
