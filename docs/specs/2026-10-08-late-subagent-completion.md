# 主回合结束后的子任务完成事件

## 真实复现

Claude Code 2.1.195 的交互式单会话回合，在临时目录中只回复 `PING`，不调用工具。
主回合的 `Stop` 已把诊断状态变为“等待输入”，会话记录完成证据也已接受；
随后同一会话的 `SubagentStop` 被归为 `hook.active`，再次变成“工作中”，
JSONL 监听器重新安装为 1。约一分钟后的空闲通知才恢复为等待输入。
这里只确认收到的协议事件及裁决，不推断子任务具体用途。

原诊断只保留 `hook.active`，无法辨别这次反跳的来源。因此本轮同时补充了
Hook 的具体事件名。安装版诊断直接显示了
`Stop → 等待输入 → SubagentStop → 工作中`，证明问题不只是界面动画。

## 修改边界

- `SessionLifecycleObservation` 和追踪记录增加预定义 Hook 事件名；诊断页及报告沿用
  原来的 evidence 字符串，追加具体协议名。非 Hook 来源不能附带 Hook 名称。
- 任意未知事件字符串都丢弃，避免把路径、对话或工具输入混入诊断。
- `SubagentStop` 只允许维持已有工作/审批状态，不能单独重启空闲、等待输入或已结束的主回合。
- 忽略这种回调时，不推进主回合的时间边界，不清除完成时间，不重新安装监听器。
  子任务本身的既有工具收尾逻辑保留。
- 真正的新 `UserPromptSubmit` 仍可恢复工作；新回合中的子任务完成也不应停止该回合。

本轮未改动用户的全局 Hook 配置、默认审批策略、模型或凭据。

## 自动化验收

新增测试覆盖已完成父回合、已中断父回合、真正的新回合继续工作、监听器安装次数，
以及 Hook 名称完整传递、未知字符串过滤、非 Hook 来源过滤。
全套 253 项 Swift、79 项 Bridge、5 项 verifier 测试通过，Release 构建、
发布元数据检查及 `git diff --check` 通过。

首次 GitHub CI 在新增测试的两项原始 `Date` 精确相等断言失败：协议使用 Unix epoch 秒，
Foundation 使用参考 epoch，转换在该 runner 上引入微小精度差异。
改为比较迟到回调前后的实际存储时间边界，并断言完成边界存在；保留对状态、
拒绝原因及监听器安装次数的严格断言，不用时间容差掩盖状态推进。

## 修复后的安装态复验

安装版为当前源码构建的 Release，ad-hoc 签名，非公证发行。安装包与构建产物的
主二进制 SHA-256 一致：
`171d9d47e578bad75babc507a13ea3bffb8793354bac73974515b40cd8f88083`。
原应用先从菜单退出并确认进程/socket 消失，再保留可恢复备份并更新安装版。

在同一临时目录新建真实交互会话，先只回复 `PING`：诊断明确显示 `Stop` 接受，
随后的 `SubagentStop` 因“子任务完成不能重启主回合”被忽略；保持等待输入、监听器 0。

接着在这个仍存活的 CLI 进程/会话中启动有限等待 Bash 工具，确认工作中、监听器 1。
UTC `03:04:00.580` 用 Escape 取消，实际 JSONL 有拒绝工具结果及用户中断标记；
`03:04:01.228` 提交下一轮（间隔 **648 ms**），`03:04:02.205` 新工具开始。
旧工具进程已消失，新工具仍在时诊断为工作中、监听器 1；中断裁决接受，
新 `UserPromptSubmit` 将空闲转回工作中。

可控释放后，`03:04:22.574` 得到 `is_error: false` 的工具成功结果，
`03:04:23.083` 回复 `OK`。UTC `03:04:33` 刷新诊断，Stop 与会话记录完成证据均已接受，
迟到的 `SubagentStop` 再次被忽略，等待输入、监听器 0。之后正常退出测试 CLI。
测试不修改项目文件，用户的全屏显示选项仍为开启、默认审批仍为完全信任。

本轮证明本机单会话的这条真实路径；不覆盖双会话并行、审批允许/拒绝/超时、
强制迟到的旧中断回调，也不等于刘海动画逐帧验收。

## 快速中断的新回合证据

修复前，在同一交互 CLI 进程/会话中运行有限等待脚本，发送 Escape 取消旧工具，
随后立即提交下一轮：

| UTC 时间 | 实际证据 |
| --- | --- |
| 02:46:21.587 | 旧工具返回 `is_error: true` 的用户拒绝结果 |
| 02:46:21.588 | 用户中断标记进入真实 JSONL |
| 02:46:22.231 | 同会话下一轮提示提交，距中断标记 643 ms |
| 02:46:23.174 | 新 Bash 工具开始 |
| 02:46:35 | 新工具仍在运行；诊断显示工作中、监听器 1 |
| 02:46:43.555 | 可控释放后工具成功，`is_error: false` |
| 02:46:44.130 | 最终回复 `OK` |

诊断同时记录中断裁决“工作中 → 空闲”、新活动“空闲 → 工作中”。
这证明真实快速切换时新工具未被已处理的旧中断误收起；没有人为制造延迟回调，
所以不能声称真实验证了任意迟到 interrupt 的拒绝。该边界仍由隔离测试覆盖。

这一轮结束后仍被 `SubagentStop` 反跳，因此完整链路在修复前不算通过。
另一个等待试验在观察间隔内超时，且工具层自动转入后台，也不计为成功验收。
