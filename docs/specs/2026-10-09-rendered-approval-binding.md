## 静态风险

`ChatView` 的会话是可更新的 `@State`。普通审批卡显示的是当次请求，
但旧回调执行 `approvePermission()` / `denyPermission()` 时重新读取
`session.pendingToolId`。若 UI 渲染与队列更新之间存在窗口，或退出动画中的旧控件
仍能调用回调，就可能把新队首的 ID 交给后端，绕过已有的 expected-ID 校验。
问答/计划卡的拒绝回调也走这条动态查询路径。

此外，原先自动审批按钮先修改会话审批模式，再发起后端请求校验；
即使对应请求已失效，也可能先影响后续审批策略。

## 修改边界

- `PermissionContext.bindAction` 只捕获渲染时的请求 ID。
- 普通审批卡的输入、身份和三个按钮来自同一个不可变 context 快照。
- 允许一次、自动审批、拒绝，以及问答/计划卡拒绝均传递原请求 ID；
  不再在按钮回调中读取当前队首。已有问答提交/批准计划的精确 context 绑定保留。
- 自动模式设置移入 `ClaudeSessionMonitor.approvePermission`：
  先读取当前有效审批并验证原请求 ID，再允许设置该会话的自动模式。
  问答与计划确认不接受该自动模式快捷操作。
- 不修改全局默认审批、Socket 协议、FIFO 排序、页面外观或退出动画。

## 隔离回归

新增 3 项 Swift 测试：

1. 第一张卡的三个生产绑定回调在 context 更新为第二项后，仍发出第一项 ID；
   第二张卡的新回调才发出第二项 ID。
2. 已关闭问答卡的拒绝绑定仍只发出原 ID，不查询新 context。
3. 第一项 Socket 失效后，迟到允许、拒绝、再次失败都不消费第二项，
   当前请求 ID 与显示输入仍为第二项。

前两项直接运行生产 `bindAction`，第三项运行无持久化、无文件同步的 SessionStore。
测试不使用用户真实会话、生产 Socket 或全局审批设置。
它们证明回调绑定和状态边界，不证明 SwiftUI 实际点击/动画，
也不单独证明自动模式设置在真实异步时序中的最终效果。
