# 全屏显示开关与验收边界

日期：2026-10-01

## 本轮范围

- 「设置 → 通用」新增「全屏时显示刘海」，中英文说明保持一致。
- 新用户默认开启，保留原有显示行为；选择写入本地偏好，重启恢复。
- 开关仅改变刘海窗口的全屏空间策略，不停止会话监听、任务或通知声音。
- 使用 AppKit 的 `fullScreenAuxiliary` / `fullScreenNone`，保留跨桌面、层级与非激活面板行为。
- 空间切换后若窗口不在活动空间，收起展开面板；点击、快捷键、辅助功能和自动展开均受同一展示条件限制，延迟焦点回调也不应再次激活窗口。
- 返回可展示空间后，手动展开仍能恢复原聊天。

没有新增全屏窗口扫描、屏幕录制权限、后台轮询或私有 API。
窗口策略参考 [Apple 的全屏行为说明](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/auxiliary)。

## 自动化覆盖

- 默认显示，关闭和重新开启的选择均能被新偏好实例恢复；使用隔离的 UserDefaults，不改用户设置。
- 反复切换窗口策略，两个全屏标志互斥，其他窗口标志保持。
- 模拟不可展示空间，点击、键盘、辅助功能及通知无法展开；重新允许后恢复聊天。

这些测试覆盖配置和交互保护，不模拟 WindowServer 的真实全屏空间。

2026-10-01 本地验证：243 项 Swift 测试、79 项 Bridge 测试、5 项验收脚本测试全部通过；Release 构建及发布元数据检查通过。Release 仍有既有的 `SessionStore.swift` 闭包显式 `self` 兼容性警告，本轮未改该文件。

## 安装态观察与未完成项

2026-09-30 已构建、ad-hoc 签名并安装带开关的 Release。原生设置页可见开关，初始开启；点击关闭后辅助功能树确认关闭，次日仍保留关闭值。2026-10-08 对照检查后已恢复开启。

TextEdit 空白窗口成功进入、退出原生全屏，但无法可靠核实同一活动空间的刘海可见性：界面工具可能返回其他空间的设置窗口，随后连接 Agent Notch 持续超时。进程采样显示主线程在 AppKit 事件循环中，未发现明显死锁，仍不能据此宣称视觉行为正确。

待完成的人工验收：

1. 关闭开关，进入其他应用的原生全屏，确认刘海隐藏；鼠标移到顶部、按展开快捷键、收到任务事件都不应使其出现。
2. 退出全屏，确认刘海恢复，原聊天和任务状态仍在。
3. 开启开关，重复进入全屏，确认刘海可见且可交互。
4. 分别在全屏中切换开关、快速切换 Space、多显示器独立 Space 下重复检查。

全屏检查与 Claude 工具运行中重启是独立场景。后者在 2026-10-08 补充了常规单会话实测，见[重启监听验收](2026-10-08-watcher-recovery.md)。

## 2026-10-08 单屏对照检查

同一安装版、同一个 TextEdit 空白窗口完成两组操作：

- 开关关闭：进入 TextEdit 原生全屏后，刘海窗口的辅助功能访问超时；退出全屏后立即恢复，可打开设置。该差异与全屏空间排除策略一致，但超时本身不能提供逐像素的隐藏证明。
- 开关开启：关闭设置窗口后，再次进入 TextEdit 原生全屏；刘海辅助功能入口可访问，截图可见黑色刘海及状态动画，点击「展开 Agent Notch」后出现任务列表和工作状态。
- 测试后将 TextEdit 恢复为普通窗口，并把全屏显示选择恢复为开启。

开启时的显示和手动展开已有安装态证据；关闭时的恢复已有安装态证据。关闭时顶部所有触发来源、快速 Space 切换、全屏内动态修改和多显示器独立 Space 仍需继续验收。
