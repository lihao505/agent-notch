# 全屏排除空间的展示入口一致性

## 当前状态与范围

已有「设置 → 通用 → 全屏时显示刘海」选项，默认开启、选择可持久化。
窗口使用已有 AppKit collectionBehavior 策略；本轮不重新实现全屏监测，
不引入 React、动画库、窗口扫描或新权限。

本轮只读原生界面清单明确返回 Mac 已锁屏、需手动解锁。
没有绕过锁屏，没有修改用户的全屏选项，也没有覆盖安装版。
在此限制下进行源码审查与隔离展示状态测试，不当作 WindowServer 实测。

## 复现的状态问题

`notchOpen` 已检查 `canPresentOnCurrentSpace`，但另外三条路径缺少同等保护：

| Before | After | Why |
| --- | --- | --- |
| `showApproval` 直接清除原聊天、替换内容并进入 opened | 在任何修改前校验展示条件 | 窗口层稍后拒绝，无法挽回已替换的聊天状态 |
| 会话快捷键先改聊天，再调用可能被拒绝的 `notchOpen` | 快捷键入口先校验，禁止时完全不修改 | 避免隐藏期间悄悄切换会话 |
| `notchPop` 仅检查 closed 状态 | 同时检查当前空间可展示 | 统一紧凑弹出与展开的空间约束 |

修复前新增 3 项回归均失败，出现 opened、popping 或聊天内容被修改。
它们直接运行生产 ViewModel，但把空间条件设为 false；没有真实进入全屏，
所以不能据此宣称旧版发生了可见窗口泄漏。

## 修改边界与交互规范

只在上述三个入口复用已有展示条件，不改变普通鼠标、快捷键、审批的视觉样式。
使用 emil-design-eng 的交互一致性原则：被禁止的操作不应留下隐蔽状态修改；
高频快捷键仍保持无动画。检查 frontend-design 后没有引入视觉改版。
本地 React 组件库已检查，不适用于这次原生逻辑修复；指定品牌设计和曲线动画目录缺失，
沿用项目现有的原生全屏策略与验收约定。

不改 SessionStore、Socket 决策、待审批队列、会话监听或通知声音。
因此隐藏刘海不是批准、拒绝、取消工具或停止任务；本轮没有新增延迟自动展开/重放策略。

## 回归证据

- 排除空间内到达审批：关闭态、原内容、打开来源、焦点代次不变；
  返回可展示空间后仍恢复原聊天，随后新的审批可正常显示。
- 下一/上一会话分别从独立初始状态运行：禁止时完全不变，返回后恢复原聊天；
  允许状态下下一会话仍正确切换。
- 紧凑弹出：禁止时保持关闭，允许时仍进入 popping。

全屏策略、指针与导航针对性 25 项测试通过。
完整 xcresult：268 passed、0 failed、0 skipped；88 项 Bridge、30 项 verifier 和发布闸门通过。
Release `CODE_SIGNING_ALLOWED=NO` 构建通过；仅为编译与链接，不是签名安装验收。
这些证据证明展示入口状态一致性，不证明真实全屏空间可见性、切换耗时或动画流畅度。

## 剩余实机验收

需要解锁并安装签名构建后继续：关闭全屏显示时收到真实审批、按会话切换快捷键，
确认不显示且不丢失原聊天；返回普通桌面确认任务与审批仍一致。
原全屏文档中的全屏内动态修改、快速 Space 切换、多显示器独立 Space 仍未通过验收。
生命周期矩阵中的同会话双审批、审批中重启及并行混合超时也保持待执行。
